# Практика: серверная валидация данных (инцидент «Чёрной пятницы»)

Роль: Lead-аналитик команды, разрабатывающей корпоративную систему бронирования ресурсов.

---

## 1. Матрица требований к серверной валидации

| Описание инцидента | Тип требуемой серверной проверки | Конкретное правило |
|---|---|---|
| 1. Бронь переговорной с датой начала 2026-12-01 и датой окончания 2026-11-01 | **Проверка бизнес-логики** (дополнительно: проверка формата) | `end_date > start_date`; обе даты в формате ISO 8601 (`YYYY-MM-DD`); `start_date >= текущая дата`; нет пересечения с существующими бронями этого ресурса |
| 2. Заявка на выдачу -50 ноутбуков пользователем с возрастом -5 лет | **Проверка типа данных** + **Проверка диапазона/формата** (дополнительно: бизнес-логика) | `quantity` и `age` — целые числа (integer), а не строки; `1 <= quantity <= max_per_request` (например, 5); `quantity <= остаток на складе`; `age` в диапазоне `14 <= age <= 100` |
| 3. Пользователь сам присвоил себе роль `super_admin` в JSON-запросе | **Проверка авторизации/ролей** | Роль берётся только из серверной сессии/JWT, поле `role` из тела запроса игнорируется (защита от mass assignment, белый список полей DTO); изменить роль может только пользователь с правом `admin`, проверка на сервере при каждом запросе |
| 4. В поле «Комментарий» передан `<script>…document.cookie…</script>` (XSS) | **Проверка безопасности/санитизация** | Строка проходит санитизацию (удаление/экранирование HTML-тегов); ограничение длины (например, `<= 500` символов); экранирование при выводе в HTML (`<` → `&lt;`); cookie с флагами `HttpOnly`, `Secure`; заголовок `Content-Security-Policy` |

**Вывод:** HTML5-валидация и проверки на фронтенде — только удобство для пользователя. Их можно обойти через Postman/cURL, поэтому все правила обязаны дублироваться на сервере.

## 2. Чек-лист ревью Pull Request для нового API-эндпоинта

Ответ на каждый пункт: **Да / Нет / Неприменимо**.

| № | Вопрос | Да / Нет / Н/П |
|---|---|---|
| 1 | Типы всех входных полей (число, строка, дата, boolean) проверяются на сервере, а строка вместо числа отклоняется с кодом 400? | |
| 2 | Для каждого числового поля заданы минимальное и максимальное значения (например, `quantity >= 1`, `age` в допустимом диапазоне)? | |
| 3 | Для каждой пары связанных полей проверена логика (например, `end_date > start_date`, количество ≤ остаток)? | |
| 4 | Строковые поля, попадающие в HTML-рендер, проходят санитизацию или экранирование? | |
| 5 | Для каждой строки задана максимальная длина? | |
| 6 | Принимаются только поля из белого списка (DTO), а лишние поля (`role`, `is_admin`, `id`) игнорируются или отклоняются? | |
| 7 | Права пользователя проверяются на сервере по токену/сессии, а не по данным из тела запроса? | |
| 8 | Ответы на ошибки валидации возвращают понятный код (400/403/422) и не раскрывают внутренние детали (stack trace, SQL)? | |
| 9 | На новое правило валидации написан автотест с негативным сценарием (отрицательное число, перепутанные даты, `<script>`, чужая роль)? | |
| 10 | Имена переменных и функций валидации понятны, а правила не дублируются в нескольких местах (нет «магических чисел»)? | |

Покрытие: функциональная корректность — пп. 1, 2, 3, 9; безопасность — пп. 4, 5, 6, 7, 8; читаемость — п. 10.

## 3. Архитектурное решение методом WSM (Weighted Sum Model)

### Альтернативы
1. **API Gateway** — валидация на уровне шлюза.
2. **Application Layer** — валидация в коде микросервиса бронирования.
3. **Database Constraints** — ограничения СУБД (`NOT NULL`, `CHECK`, `FOREIGN KEY`).

### Критерии и обоснование весов

| Критерий | Вес Wj | Обоснование |
|---|---|---|
| Надёжность (защита при прямом доступе к БД) | 0.35 | Главная проблема инцидента — в базу попали некорректные данные. Это самый важный критерий |
| Гибкость изменения правил | 0.25 | Бизнес-правила (лимиты, роли) меняются часто, нужно менять их без пересборки БД или шлюза |
| TCO (сложность поддержки и обучения) | 0.25 | Команда небольшая, чем проще поддержка, тем меньше новых ошибок |
| Производительность | 0.15 | Проверки простые и дешёвые, поэтому критерий менее значим |
| **Сумма** | **1.00** | |

### Матрица решений (оценки Xij по шкале 1–10, больше — лучше)

| Критерий | Вес | API Gateway | Application Layer | Database Constraints |
|---|---|---|---|---|
| Производительность | 0.15 | 9 | 7 | 6 |
| Гибкость изменения правил | 0.25 | 5 | 10 | 3 |
| TCO | 0.25 | 6 | 7 | 5 |
| Надёжность | 0.35 | 3 | 5 | 10 |

### Расчёт по формуле Si = Σ(Wj × Xij)

**API Gateway:**
S1 = 0.15·9 + 0.25·5 + 0.25·6 + 0.35·3 = 1.35 + 1.25 + 1.50 + 1.05 = **5.15**

**Application Layer:**
S2 = 0.15·7 + 0.25·10 + 0.25·7 + 0.35·5 = 1.05 + 2.50 + 1.75 + 1.75 = **7.05**

**Database Constraints:**
S3 = 0.15·6 + 0.25·3 + 0.25·5 + 0.35·10 = 0.90 + 0.75 + 1.25 + 3.50 = **6.40**

### Итоговый рейтинг

| Место | Альтернатива | Баллы |
|---|---|---|
| 1 | Application Layer | 7.05 |
| 2 | Database Constraints | 6.40 |
| 3 | API Gateway | 5.15 |

### Вывод
Лучший результат у **Application Layer** (7.05): правила легко менять, а бизнес-логику (остатки на складе, пересечение броней, роли) можно проверить только в коде сервиса. Но этот подход не защищает при прямом доступе к БД, а Database Constraints набрали 6.40 именно за надёжность. Поэтому оптимален **комбинированный подход (защита в глубину)**:

1. **Application Layer** — основная валидация (типы, диапазоны, бизнес-логика, санитизация, авторизация).
2. **Database Constraints** — последний рубеж (`CHECK (end_date > start_date)`, `CHECK (quantity > 0)`, `NOT NULL`, внешние ключи).
3. **API Gateway** — только грубая фильтрация: размер запроса, схема JSON, rate limiting.

## 4. Обновлённые пункты Definition of Done (DoD)

1. **Автоматизация:** для каждого нового или изменённого API-эндпоинта в CI-пайплайне проходят автотесты с негативными сценариями (отрицательные числа, `end_date < start_date`, лишнее поле `role`, XSS-строка `<script>`), а также статический анализ безопасности (SAST). Если хотя бы один тест или проверка не пройдены, merge блокируется.
2. **Процесс ревью:** Pull Request одобрен минимум одним рецензентом, который заполнил чек-лист из раздела 2 (все пункты «Да» или «Н/П» с пояснением), а правила валидации продублированы ограничениями в БД (миграция с `CHECK`/`NOT NULL`).
